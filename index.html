00 / Method

Comparison Methodology & Scope

Evaluation Criteria · Freestanding Execution · RTOS Boundary Laws

In mission-critical embedded systems and real-time workstations, ranking runtime libraries merely by POSIX symbol count is an architectural fallacy. A runtime that provides unbounded recursion in qsort or halts the processor inside assert/0 violates hard real-time guarantees, regardless of its compliance certificates.

This study compares C runtimes across five objective pillars: (1) Total LOC and memory footprint (.text / .bss / heap), (2) File-by-file resource consumption, (3) Suitability against POSIX process/thread/IPC models in single-address-space RTOS targets, (4) Separation of high-level text/locale services, and (5) Contemporary C99 quality/security hardening (MISRA & CERT C).

03 / POSIX Standards

The POSIX Dilemma in RTOS Markets: BTRON 3.20 vs Apache NuttX & IEEE 1003 Standard Series

Architectural Divergence · Microkernel Primitives vs Emulated POSIX · NuttX Kernel Comparison

The IEEE 1003 Standard Series was conceived for time-sharing minicomputers equipped with hardware MMUs, where process isolation supersedes deterministic latency. Forced into embedded real-time systems, POSIX primitives inflict unpredictable page-table cloning delays, stack blowouts, and severe descriptor leakage.

B-System BTRON 3.20 (./b-spec/) replaces the IEEE 1003 Standard Series with lightweight microkernel task actors, zero-copy lock-free ringbuffers, shared memory blocks, and hypermedia plane synchronization, competing directly with the POSIX emulation layer of RTOS kernels like Apache NuttX.

Level 01 · Standards Synthesis

Macro Architecture: Why Virtual-Memory Unix Fails on Real-Time Silicon

The IEEE 1003 Standard Series was originally architected for time-sharing Unix minicomputers equipped with hardware MMUs, coarse timeslicing, and fork-based process isolation. In safety-critical embedded systems and hard real-time workloads, standard POSIX primitives impose non-deterministic latency spikes: fork/0 demands copy-on-write page table replication, asynchronous thread cancellation unwinds dynamic call stacks with fatal deadlock risks, and filesystem-backed IPC queues leak descriptor table entries. BTRON 3.20 rejects this minicomputer legacy, replacing process-heavy time-sharing with lightweight, cooperative real-time task actors within deterministic memory planes—scaling seamlessly from 1 MB ROM images to SMP workstations without the fragmented compromises of POSIX Realtime Profiles (PSE51–PSE54).

Level 02 · Subsystem Efficiency

Subsystem Overhead: The Hidden Tax of POSIX Emulation in Apache NuttX

Apache NuttX represents the modern benchmark for open-source POSIX microkernels, yet its commitment to Linux-compatible abstractions introduces significant runtime overhead on microcontroller cores. Every NuttX message queue, socket, and stream must allocate a VFS file descriptor (rapidly exhausting the fixed struct file table), threads incur mandatory Thread-Local Storage (TLS) and signal mask allocations inside struct tcb_s, and message queues dynamically allocate heap nodes into linked priority lists. In contrast, BTRON 3.20 eliminates the VFS indirection layer for core IPC. Kernel objects are identified by direct, constant-time O(1) integer handles; mutual exclusion is enforced in silicon via the kernel Priority Inheritance Protocol (PIP); and shared memory is mapped in a single call (Smalloc), slashing RAM consumption and eliminating heap fragmentation during burst communication.

Level 03 · Call-Level Determinism

Function-by-Function Execution: Eliminating Multi-Call Syscall Cascades

At the system call boundary, POSIX forces developers into fragile multi-step programming sequences. Setting up shared memory requires four discrete calls (shm_open → ftruncate → mmap → close); timed synchronization demands complex timespec arithmetic subject to system clock drift; and signaling conditions under mutexes triggers thundering-herd contention or lost wakeups. As detailed below from the ./b-spec/os_spec/kernel/ specification, every BTRON 3.20 system call is an atomic, bounded contract: wai_sem/0 acquires multi-unit resource counts in one step; wai_flg/0 atomically evaluates 32-bit pattern conditions with automatic state clearing (TWF_CLR); and synchronous rendezvous ports (cal_por / acp_por) execute client-server transactions without intermediate buffer copying or thread stack duplication.

Synchronization: SEM & Flags

Atomic Multi-Bit Primitives

POSIX requires pairing pthread_mutex_t with pthread_cond_t to signal state changes, risking missed signals. BTRON 3.20 provides cre_flg/0 and wai_flg/0 with atomic 32-bit AND/OR patterns and automatic clear (TWF_CLR), while wai_sem/0 accepts exact millisecond timeouts (TMOUT) with multi-unit acquisitions.

05 / Missing Parts

Missing Parts: Deliberate Architectural Omissions

International Encodings · Font Separation · Attack Surface Elimination

In standard libc distributions (glibc, musl), international text encodings, iconv, and locale collation tables are statically linked or dynamically loaded into the lowest runtime layer. In an embedded RTOS, this architectural mistake inflates firmware size by several megabytes and exposes the microkernel to critical memory vulnerabilities.

B-System treats character encodings, Unicode tables, and font management as high-level workstation presentation services (TAD, HMI, and Mozc IME). The C runtime layer remains 100% encoding-agnostic, operating strictly on raw, validated byte buffers.

Memory Conservation

Elimination of Megabyte Tables

The Unicode 15/16 Character Database (UCD), case folding, normalization (NFC/NFD), and collation tables consume 1.8 MB to 4.2 MB of flash. Moving them to the HMI/TAD presentation plane leaves rt at negligible kilobyte scales.

06 / Quality Review

Security & Quality Review: The Golden Middle Way

MISRA C:2023 · CERT C Mitigations · Non-Recursive Determinism · Hardware Errata Safety

Contemporary real-time software engineering requires runtimes to comply with functional safety benchmarks (IEC 61508, ISO 26262, DO-178C). Traditional libcs frequently violate basic safety rules through recursive quicksort algorithms, uncontrolled heap allocations, and unconditional processor halts on failed assertions.

B-System include/rt embodies the "Golden Middle Way": neither an over-bloated Unix monolith full of hidden CVEs, nor an incomplete toy stub. It provides verified safety mechanics engineered specifically for high-integrity embedded cores and mission-critical workstations.

The Golden Middle Way: In safety-critical RTOS design, perfection is achieved not when there is nothing more to add, but when there is nothing left to take away without compromising correctness. include/rt provides exactly the mathematical and string primitives modern C99 compilers demand, while eliminating every mechanism known to cause non-deterministic failure in embedded flight.

09 / OpenGL ES Graphics

Workstation 3D Acceleration: Multi-Backend OpenGL ES 2.0

Embedded Silicon Drivers · Zero Mesa/DRM/X11 Overhead · Direct Register DMA

Real-time workstations demand responsive, hardware-accelerated 3D graphics for flight instruments, medical imaging, and spatial user interfaces. In conventional Linux environments, deploying OpenGL entails dragging in the entire Mesa 3D graphics stack, the DRM/KMS kernel subsystem, Wayland/X11 protocols, and a multi-megabyte LLVM shader compiler—totalling over 200 MB of binary disk bloat.

B-System breaks this dependency chain by delivering a clean, direct-to-metal OpenGL ES 2.0 runtime operating across five hardware and virtualization backends. Each backend compiles to a self-contained translation unit with zero external library dependencies, consuming under 50 KB of compiled code.

Zero-Dependency 3D Architecture

Eliminating the 200 MB Mesa Stack

Standard Linux desktop graphics stacks require libGL.so, libEGL.so, libdrm.so, the Linux KMS kernel driver, and LLVM-based JIT compilers for shader execution. On embedded RTOS targets where flash storage is measured in tens of megabytes, this stack is prohibitive. B-System drives GPU hardware registers directly through kernel device handles, ensuring that standard 3D rendering, texture mapping, and frame composition operate with deterministic memory overhead.

Unified Window Compositor

One Surface API, Five GPU Implementations

The B-System window compositor (compositor.h) presents a single damage-tracked surface interface to interactive applications. The active graphics backend is dispatched transparently: texture uploads, alpha blending, and double-buffered presents route through unified function pointers whether drawing to a high-speed Broadcom V3D tile buffer, a VirtIO-GPU ring, or the PS2 Graphics Synthesizer.
