Faster than C library.

On this machine rt is the faster library against the C library macOS ships. The NEON kernels, qsort, the number parsers, snprintf, and the pool allocator beat it. Coefficient is libc time divided by rt time.

00 / Method

One machine, one opponent

scripts/run.sh · Darwin arm64 · Apple clang 21.0.0 -O2

The host oracle compiles the scalar C with src/aarch64/neon/mem.S and string.S, then times each call against the C library on this Apple M4. Flags are -std=c99 -O2 -Wall -Wextra -Werror -fno-strict-aliasing -fno-builtin. SVE is not available here, and the run skips it. macOS 27.0.1.

The libc column is that shipped library. musl, glibc, and the other runtimes in the study are not in this timing. A row is faster when the unrounded coefficient is at least 1.05, parity inside 5 percent, and slower at 0.95 or below. Every printed time in this run is a multiple of 1,000 ns.

This is a synthetic host oracle on one Apple M4. It is not a SPEC submission. The strcpy row does not call libc strcpy. The buffer is 512 bytes with the NUL in the last byte, and the libc side is memcpy of that counted length. rt_strcpy is the function under test, and on this run it is slower. rt_qsort_simple stays in the library. It is absent from the runs and from the tables. The sort row is qsort only.

01 / Faster

Where rt beats the shipped library

Unrounded coef ≥ 1.05 · same numbers as the oracle print

Apple M4 · libSystem

Eleven rows, zero failures

NEON memcmp, strlen, and strcmp are the wide gaps. qsort is 120,000 ns against 83,000 ns for libc qsort on the same 512-int input. snprintf is 7,000 against 3,000. The pool allocator is 4,000 against 1,000 for the 64-byte malloc/free loop. NEON memcpy and strchr win by a single microsecond, which is one step of this printout.

The allocator row is a fixed 8,192-byte pool against the system allocator. It is a faster allocate-and-free loop on this input. It is not the same allocator. Numeric, format, and allocator rows are one sample, not a median of 21.

02 / Scalar

The portable C, including the losses

Apple’s libc is already vector code · scalar loops lose on memory and most strings

The scalar backend is the C in src/common/scalar. On this M4 it loses the memory kernels and most of the string kernels to the shipped library. That is the measurement. The NEON objects above are what this machine runs for those calls.

strstr prints 1.05. The unrounded ratio is 156,000 / 149,000 = 1.047, inside the parity band, so the row is not counted as a win. memset is 8,000 against 8,000.

03 / NEON

The kernels this M4 runs

src/aarch64/neon · memory and string · scalar baseline is the table above

The neon objects linked on this machine are memcpy, memset, and memcmp, plus strlen, strcmp, and strchr. There is no neon memmove in that link, so the oracle prints no neon memmove row.

The oracle repeats the scalar numeric, sort, format, and allocator rows on the neon table, with the same times. They are one measurement. They are listed once, in the scalar table.
