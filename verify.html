Binary verification · Coq

Prove the bytes.

A plan for the rt memory kernels, and one proof that is already checked. make verify runs Coq on rt_memset_neon for every fill byte and every length below 264. The returned pointer is the start of the buffer, address 0 in this model. memcpy, memcmp, and the rest of the plan are still open.

00 / Papers

Three machine models

A submodel of the CPU · a binary, then a theorem · a formula, then a search

The checker is Coq, standard library only. The object is one vector kernel whose bytes are already frozen. A change that makes coqc slow is too big for this kernel.

Lean 4, CompCert, VST, Iris, and a C parser are larger than the function they would be asked to justify. They stay outside this file.

PPDP 2013 · Coq

CoqASM — a machine submodel

Andrew Kennedy, Nick Benton, Jonas B. Jensen, and Pierre-Évariste Dagand, “Coq: The World’s Best Macro Assembler?”, PPDP 2013. The paper builds a submodel of a subset of x86: an instruction interpreter, an encoder to concrete bytes, and a separation-logic assertion above those bytes. Assembly notation elaborates inside Coq. The theorem says the bytes establish the assertion. That development is a general assembler. It is not an input to rt_memset_neon. The shared technique is the submodel itself: a step relation small enough that a person can read the statement. Their type classes and SSReflect stay in their paper.

TPHOLs 2009 · HOL4

Verified LISP — binary, then theorem

Magnus O. Myreen and Michael J. C. Gordon, “Verified LISP Implementations on ARM, x86 and PowerPC”, TPHOLs 2009, LNCS 5674. The proofs are in HOL4. Each instruction of a Lisp 1.5 interpreter, including its allocator, is related to one step of a small operational semantics. The object is a language runtime. The method is the one used here for a vector kernel: take the binary that already exists, interpret its bytes, and prove that the interpreter meets a functional specification. verify/models/MemsetNeon.v is that method on 56 ARM64 words, in Coq.

Proc. IEEE 2005 · CoqPL 2021

SPIRAL — formula, then search

Markus Püschel and colleagues, “SPIRAL: Code Generation for DSP Transforms”, Proceedings of the IEEE, 2005. Patrick Brinich and Jeremy Johnson, CoqPL 2021. SPIRAL’s semantic model is a formula in SPL, a sparse factorization of a linear transform over a vector tract. A search rewrites the formula. The factorization that wins the cost model is emitted as a vector kernel. The binary is the output of the search. Brinich and Johnson verified a slice of that pipeline in Coq: formula, rewrite, generated code. This library runs the pipeline in the other direction. The kernel is written, measured against the shipped C library, and frozen. Coq then models those frozen bytes. The prover does not search for the kernel.

CoqASM contributes the machine submodel. Verified LISP contributes the order: binary first, theorem second. SPIRAL contributes the picture of a vector body as a repeated width plus a tail, and it contributes that picture as a search. The memset proof uses the picture as the control flow already present in src/aarch64/neon/mem.S.

01 / Rule

Small, and fast to check

One file · induction on the 64-byte and 16-byte loops

02 / Order

Order of work

SIMD · C99 contract · security · Coq model · tune

A kernel is born as instructions. The proof is a model of the binary that survived measurement and the static scan. A later step reads the artifact the earlier step froze.

Strings that walk to NUL, stdio, qsort, and the allocator stay on the host oracle. They are outside the vector-kernel model.

A decompiler lift of an existing routine, such as glibc strlen, can follow this kernel. The kernel is the bytes we ship.

03 / Memset

The checked argument

rt_memset_neon · 56 words · every n below 264

init b n places the buffer at address 0, the fill byte in x1, the length in x2, and n zero bytes in memory. halted is three facts: ret has run, x0 is 0, and memory is n copies of the byte. The 0 in x0 is the saved base. The prologue copies the incoming pointer into x8, and the epilogue is mov x0, x8; ret.

Fuel is exists k. The vector-store flag is outside the statement. So is any byte past n.

0 · Contract

The example the other kernels follow

b is c truncated to a byte. The call returns the original pointer and stores b at every index below n. A byte outside that range stays as it was. That third line is the host canary. The checked theorem is the first two lines, with the buffer at address 0 and n < 264, so the returned x0 is 0. Neon memset is parity with the shipped library. This plate is the contract, not the proof.

1 · Statement

Main theorem

One statement covers every fill byte and every length that fits in x2. The corollary at n = 16 is the old statement, closed by imm_bound. A bare call to lia does not invent a witness for a concrete power of two.

2 · Spine

Main lemmas

The file has a lemma per instruction form and a lemma per label in the assembly. The argument a reader has to hold is the spine below. canon is the invariant between labels: x0 is how many bytes are filled, x2 is how many remain, the vector register is the splat of the byte, and memory is the filled prefix followed by a zero suffix.

3 · Descent

By bitness

The length is one machine word. The proof follows the widths the binary already peels. At width w, Nat.div_mod writes the remainder as w·q + r with r < w. The loop lemma inducts on q. The base case is one body. The step is one body, then the induction hypothesis, after the sum (filled + w) + w·q is lined up with filled + w·(q+1).

4 · Reduction

What survives on AArch32

The NEON q register is 128 bits on AArch32 and on AArch64, so a 16-byte store is still one instruction. The 16-row bit table talks about a remainder, and it does not mention the address width. This tree has no AArch32 memset. The reduction is the cut between lemmas that mention encodings and lemmas that mention only canon.
